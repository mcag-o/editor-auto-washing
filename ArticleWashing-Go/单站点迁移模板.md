# 单站点迁移模板

本文档是 `爬虫开发和接入.md` 的配套执行模板。

用途：当后续开发人员准备把某一个 `DataCollection` 平台迁移到 `ArticleWashing-Go` 时，可以直接按本文档逐项推进，不需要自己重新拆阶段。

建议使用方式：

- 复制本文档作为某个平台的工作草稿
- 把文中的“平台名 / source id / 旧实现路径”替换成实际值
- 按阶段逐项勾选
- 每完成一个阶段，补测试并提交

---

## 0. 平台基本信息

在开始前，先把下面信息填完整。

- 平台名称：`<平台中文名>`
- source id：`<source-id>`
- 平台类型：`json-api / html / hybrid`
- 是否需要认证：`none / cookie / header / token / other`
- 是否支持 detail：`yes / no / unknown`
- 旧实现参考：`DataCollection/src/platforms/<xxx>.js`
- 目标状态：`implemented-equivalent / implemented-partial`

补充说明：

- 这个平台当前在 Go 侧是 `placeholder` 吗：`yes / no`
- 这个平台是否已经有 fixture：`yes / no`
- 这个平台是否属于优先迁移平台：`high / medium / low`

---

## 1. 迁移总目标

该站点迁移完成后，应满足：

- 不再依赖 `DataCollection` 旧脚本运行
- 进入 `ArticleWashing-Go` 统一 collector runtime
- 具备至少 hotlist 能力
- 如业务需要，具备 detail/article 能力
- 使用统一配置、统一 auth、统一 HTTP、统一 retry 路径
- 有 fixture、有测试、有 health、有可定位错误信息

---

## 2. 阶段拆分总览

建议严格按下面 6 个阶段推进：

1. 平台调研与能力盘点
2. 配置与占位信息整理
3. hotlist 实现
4. detail/article 实现（如需要）
5. runtime 接入与测试补齐
6. 状态收口与替代确认

不要跳阶段直接“先写代码再补配置”。

---

## 3. 阶段一：平台调研与能力盘点

目标：先弄清这个平台在旧系统里到底做了什么，不要靠印象迁移。

### Checklist

- [ ] 确认旧实现文件位置
- [ ] 确认热榜接口或热榜页面 URL
- [ ] 确认 detail 接口或 detail 页面 URL
- [ ] 确认该平台需要的 headers / cookie / token
- [ ] 确认该平台是否有特殊 UA / Referer / anti-bot 要求
- [ ] 确认旧实现里是否存在额外 query 参数或签名逻辑
- [ ] 确认旧实现输出的字段有哪些
- [ ] 确认是否已有 fixture 可复用

### 本阶段产出物

- 一份平台能力说明，至少写清：
  - hotlist 来源
  - detail 来源
  - auth 需求
  - 旧实现路径
  - 已知失败模式

### 本阶段注意事项

- 不要先写插件
- 先把“旧平台到底怎么工作”弄明白
- 如果旧实现本身不稳定，先把不稳定点记入 TODO

---

## 4. 阶段二：配置与占位信息整理

目标：先把该平台纳入 Go 侧统一配置体系。

### 需要修改的地方

- `ArticleWashing-Go/infra/config/collector_config.go`
- `ArticleWashing-Go/config/config.json`

### Checklist

- [ ] 在 `collector_config.go` 中确认或补齐该平台 `CollectorSourceDef`
- [ ] `display_name` 已填写
- [ ] `aliases` 已填写
- [ ] `source_type` 已填写
- [ ] `source_url` 已填写
- [ ] `status` 已填写为当前真实状态（通常开始时是 `placeholder`）
- [ ] `goal` 已填写中文工作目标
- [ ] `todo` 已填写下一步开发清单
- [ ] `notes` 已填写注意事项
- [ ] `migration_reference` 已指向旧实现
- [ ] `supports_article` 已根据真实情况填写
- [ ] `auth_mode` / `auth_profile` 已按平台需求配置
- [ ] `config/config.json` 中存在该平台 source 配置
- [ ] 已指定 `http_client`
- [ ] 已指定 `retry_policy`
- [ ] 已指定 `auth_profile`
- [ ] 已配置 `timeout_ms`
- [ ] 已配置 `hotlist_limit`

### 本阶段产出物

- 该平台 source 定义完整进入统一配置层
- 中文工作目标和 TODO 可直接指导后续开发

### 本阶段验收标准

- [ ] 配置校验通过
- [ ] 该平台可在 source catalog 中被识别
- [ ] 后续开发者只看配置就能知道要做什么

---

## 5. 阶段三：hotlist 实现

目标：先做出最小可用的真实热榜抓取能力。

### 需要修改的地方

- `ArticleWashing-Go/collector/plugin/sources/<platform>.go`
- 如有必要，`ArticleWashing-Go/collector/plugin/sources/api_plugin.go`
- 如有必要，`ArticleWashing-Go/collector/html/...`
- 测试文件与 fixture

### Checklist

- [ ] 新增或替换真实插件实现
- [ ] 实现 `SourceID()`
- [ ] 实现 `DisplayName()`
- [ ] 实现 `Aliases()`
- [ ] 实现 `FetchHotlist()`
- [ ] 实现 `NormalizeHotEntry()`
- [ ] 实现 `HealthCheck()`
- [ ] 实现 `Capabilities()`
- [ ] 实现 `Descriptor()`
- [ ] 如果需要 runtime client 注入，支持 `WithHTTPClient()` / `HTTPClient()`

### hotlist 输出最低要求

- [ ] `SourceID`
- [ ] `ExternalID`
- [ ] `CanonicalURL`
- [ ] `Title`
- [ ] `Summary`（如可得）
- [ ] `Rank`（如可得）
- [ ] `RawJSON` 或等价 raw 信息
- [ ] 必要 `Metadata`

### hotlist 测试清单

- [ ] 正常 hotlist fixture 测试
- [ ] 空列表或结构异常测试
- [ ] `HealthCheck()` 成功测试
- [ ] `HealthCheck()` 失败测试

### 本阶段验收标准

- [ ] 该平台能够进入 run 主流程
- [ ] 能生成 collector entries
- [ ] source health 能正常反映可用性
- [ ] 不再依赖 placeholder hotlist 行为

---

## 6. 阶段四：detail/article 实现（如需要）

如果该平台只需要热榜，不必强行实现 detail。

如果该平台后续需要 bridge 到文章工作区，则通常需要 detail/article。

### Checklist

- [ ] 确认 detail 来源（API / HTML / hybrid）
- [ ] 实现 `FetchArticle()`
- [ ] 实现 `NormalizeArticle()`
- [ ] 返回完整 `RawArticle`
- [ ] 提供 `ContentType`
- [ ] 必要 metadata 已保留
- [ ] detail fixture 已补充
- [ ] article normalize 测试已补充

### detail 完成后的最低验收

- [ ] 可从 entry 拉取 article
- [ ] 可得到标准化文章内容
- [ ] 如需要，能进入 bridge 主流程

---

## 7. 阶段五：runtime 接入与统一链路验证

目标：确认该平台不是“插件能跑”，而是“已经真正接入主系统”。

### Checklist

- [ ] `PolicyResolver` 能正确解析该平台配置
- [ ] `AuthFactory` 能处理该平台 auth 需求
- [ ] `HTTPFactory` 能为该平台构造 client
- [ ] `runtime_plugin_adapter` 能把 client 注入插件
- [ ] `RunService` 能走真实 runtime path
- [ ] `SourceRegistryService` 能走真实 runtime-aware health path
- [ ] source sync 持久化 metadata 正确
- [ ] 若该平台有默认 profile / source override，解析结果正确

### 测试清单

- [ ] resolver 测试
- [ ] auth factory 测试
- [ ] HTTP factory 测试
- [ ] run service 测试
- [ ] source registry health 测试
- [ ] source sync metadata 持久化测试

### 本阶段验收标准

- [ ] 该平台真实运行时已走统一配置/认证/HTTP/重试路径
- [ ] 插件内部不再自己解析 secret
- [ ] 插件内部不再自己偷偷实现独立 retry/auth 逻辑

---

## 8. 阶段六：状态收口与替代确认

目标：把该平台从“迁移进行中”收口成一个明确状态。

### Checklist

- [ ] 若 placeholder 还存在，已被真实插件替代
- [ ] `status` 从 `placeholder` 更新为 `partial` 或 `implemented`
- [ ] `goal` / `todo` / `notes` 已更新为当前真实状态
- [ ] `collect.md` / 相关迁移文档如有必要已同步
- [ ] 如果该平台已达到等价替代水平，明确记录

### 状态定义建议

- `placeholder`
  - 只有占位和说明，无真实实现
- `partial`
  - 有真实实现，但只覆盖部分能力，例如 hotlist-only
- `implemented`
  - 已覆盖当前目标能力，进入稳定维护阶段

### 替代确认建议

只有满足以下条件，才建议说“该平台已完成 Go 迁移”：

- [ ] hotlist 已完成
- [ ] detail（如需要）已完成
- [ ] auth 已完成
- [ ] 统一 runtime 接入已完成
- [ ] fixture 已完成
- [ ] 回归测试已完成
- [ ] 不再依赖 `DataCollection` 旧脚本

---

## 9. 单站点迁移模板（可复制填写）

下面这段可以直接复制，作为某个平台的开发清单。

```md

- source id: `<source-id>`

- 认证: `none / cookie / header / token`

- 当前状态: `placeholder / partial / implemented`

## 阶段一：调研

## 阶段三：hotlist

## 阶段四：detail
```

---

## 10. 每次迁移完成后的最小提交建议

推荐按阶段提交，而不是一次性堆大提交。

建议的提交粒度：

1. `feat: add <source-id> collector config scaffold`
2. `feat: implement <source-id> hotlist plugin`
3. `feat: add <source-id> article fetch support`
4. `test: add <source-id> fixtures and runtime coverage`
5. `docs: update <source-id> migration status`

---

## 11. 最后提醒

单站点迁移最容易犯的错误有三个：

1. 只写抓取逻辑，不接统一 runtime
2. 只写成功路径，不补 fixture 和失败测试
3. 把 secret、retry、timeout 又重新硬编码回插件内部

只要避免这三个问题，并按本文档阶段推进，这个站点就能稳定纳入 `ArticleWashing-Go`，而不是再产生一个新的“孤立爬虫实现”。
