# ArticleWashing-Go 采集融合方案审计报告

> 审计时间：2026-04-11  
> 审计对象：`ArticleWashing-Go` 当前 collector 融合实现、`README.md`、`对比.md` 及其相关运行时设计  
> 审计目标：识别当前 DataCollection 向 `ArticleWashing-Go` 融合方案在扩展性、容错机制、并发安全、配置管理、可观测性与交付可信度上的缺陷与风险，并提出可执行的整改建议。

---

## 一、执行摘要

当前 `ArticleWashing-Go` 已经从“内容处理中台”演进为“内容处理中台 + Go 原生采集器”的统一运行时，整体方向正确，技术选型也基本合理。尤其是以下几点已经具备了明确的平台雏形：

- 基于 `SQLite + repo + service + HTTP/CLI` 的统一运行时已经形成
- 采集链路已从单阶段热点抓取扩展为两阶段模型：`hotlist -> detail fetch -> bridge`
- 已具备 source registry、scheduler skeleton、HTML source、Cookie-auth source、bridge into workspace 等关键能力
- 已能与 `ArticleWashing-Go` 原有 workspace / formatting / review / publish 主链路形成可用衔接

但从生产可用性与长期可维护性角度审视，当前实现**仍不应被表述为完整生产完成态**。主要问题不在于“完全没有能力”，而在于以下方面仍存在结构性短板：

- collector 对外运行面与内部服务面之间存在明显落差
- 调度闭环、恢复能力、任务编排与 bridge 一致性仍不足以支撑完整生产切换
- 配置管理与 source 生命周期模型仍偏运行时拼接
- 文档已经比之前真实，但仍需持续区分“内部已实现能力”和“对外运维入口”
- 测试数量不少，但对真实运行边界、恢复语义、并发压力和 cutover 条件的验证仍偏弱

结论：

- **架构方向正确**
- **当前版本适合作为后续 Go 主平台继续演进**
- **当前版本尚不应被直接视为“采集系统生产迁移已完成”**
- **在正式切换前仍需一轮以运行闭环、恢复机制、配置治理和可观测性为中心的整改**

## 三、第一部分：严格问题审计

### P0：生产切换阻塞项

#### P0-1：collector 对外运行面与内部能力不一致，不能支撑“已完成生产替代”表述

- **问题描述**：当前 collector 的 source registry、run listing、scheduler control 已经对外暴露，但 detail fetch 与 bridge 仍主要停留在内部 service 层，不是完整的一线运维入口。
- **影响范围**：运维无法通过统一 HTTP/CLI 正式控制 `entry -> article -> workspace` 全链路；生产切换表述容易产生误导。
- **证据路径**：
  - `ArticleWashing-Go/README.md:21`
  - `ArticleWashing-Go/README.md:66`
  - `ArticleWashing-Go/README.md:246`
  - `ArticleWashing-Go/README.md:315`
  - `ArticleWashing-Go/service/collector_runtime.go:10`
- **根因分析**：Task 4 已实现 detail fetch/bridge 服务，Task 6 又主动修正文档真实性，因此当前状态是“内部能力已实现，但运维入口未完全开放”。
- **建议**：
  - 增加正式 collector operational API / CLI：
    - `collector entries list`
    - `collector articles list`
    - `collector detail-fetch run/retry`
    - `collector bridge run/retry/status`
  - 为内部服务与外部运维接口建立一一映射清单
  - 在未完成前，严禁使用“已完成 DataCollection 生产替代”表述

#### P0-2：DataCollection 全量 source inventory 尚未迁完，当前不能称为功能全量替代

- **问题描述**：当前迁入 Go runtime 的 source 仅包含少量站点，且其中部分还是 hotlist-only。
- **影响范围**：若过早退役 `DataCollection`，会直接丢失未迁移 source 的采集能力。
- **证据路径**：
  - `ArticleWashing-Go/README.md:69`
  - `ArticleWashing-Go/README.md:80`
  - `ArticleWashing-Go/对比.md:118`
  - `ArticleWashing-Go/对比.md:127`
- **根因分析**：当前 collector migration matrix 是“首批迁移状态”，不是“全量站点完成状态”。
- **建议**：
  - 将生产切换前置条件明确写死为：
    - critical sources fully migrated
    - 每个 source 至少具备 fixture、health、run、detail fetch（如适用）、bridge 验证
  - 在 cutover checklist 中加入 `DataCollection-only sources = 0`

#### P0-3：scheduler 仍是 skeleton，缺少生产级恢复与任务恢复能力

- **问题描述**：当前 scheduler 已具备 `run-once / daemon / stop / status / health`，但仍然缺少任务恢复、崩溃恢复、重入恢复、持久化队列重放等生产级行为。
- **影响范围**：进程崩溃、意外退出、长任务中断后可能出现 state 仍在、执行上下文却已丢失的问题。
- **证据路径**：
  - `ArticleWashing-Go/collector/scheduler/service.go:15`
  - `ArticleWashing-Go/README.md:88`
- **根因分析**：当前 scheduler 更像“可运行原型”，而不是完整任务编排系统。
- **建议**：
  - 将 scheduler 拆成：
    - schedule planner
    - persisted job queue
    - execution worker
    - recovery manager
  - daemon state 不应只依赖 scheduler snapshot，应与真实 pending/running tasks 关联

### P1：高风险设计缺陷

#### P1-1：插件配置模型仍偏运行时拼接，尚未形成稳定 contract

- **问题描述**：当前通过 `SourceConfigurablePlugin` 让 plugin 直接接收 `domain.CollectorSource` 做运行时配置覆盖，抽象边界仍偏宽。
- **影响范围**：未来 source 配置项增多后，plugin 接口会逐步与 domain model 强耦合，source 生命周期与配置演进会难以维护。
- **证据路径**：
  - `collector/plugin/interface.go`
  - `collector/service/source_registry_service.go`
- **根因分析**：为快速打通 `cookie_secret_ref` 等 persisted auth config，采用了最直接的 override 方式。
- **建议**：
  - 引入独立的 plugin config DTO，而不是直接传递 `domain.CollectorSource`
  - 将配置拆分为：
    - source metadata
    - runtime auth config
    - crawl behavior config
    - clean/normalize config

#### P1-2：bridge 仍依赖补偿而非真正事务边界

- **问题描述**：当前 bridge 已通过补偿机制降低风险，但仍属于“补偿式一致性”，不是“事务式一致性”。
- **影响范围**：在 workspace create 成功、collector article update 失败时，系统依赖补偿删除 workspace record；在真实生产中仍有边缘失败窗口。
- **证据路径**：
  - `collector/service/bridge_service.go`
- **根因分析**：collector repo 与 workspace repo 之间没有统一事务边界。
- **建议**：
  - 设计 bridge transaction boundary
  - 或引入 `bridge_pending / bridge_applied / bridge_reconcile_needed` 状态机
  - 增加专门 reconciliation job，而不是完全依赖即时补偿

#### P1-3：detail fetch 与 scheduler 之间的任务编排仍弱耦合

- **问题描述**：当前 hotlist、detail fetch、bridge 都已经有 service，但没有形成统一、稳定、可持久化的 collector DAG/queue model。
- **影响范围**：source 与 entry 数量增大后，难以优雅支持：
  - hotlist 完成后的大规模 fan-out detail jobs
  - detail fetch retry
  - bridge retry
  - per-source backpressure
- **证据路径**：
  - `collector/service/run_service.go`
  - `collector/service/article_fetch_service.go`
  - `collector/scheduler/service.go`
- **根因分析**：阶段任务已经存在，但尚未抽象为统一的 collector task model。
- **建议**：
  - 引入 collector task 表，或复用现有 job runtime 承载 collector stages
  - 显式建模：
    - `hotlist_task`
    - `detail_task`
    - `bridge_task`

#### P1-4：SQLite 单库承载 collector 与 content-hub 全部状态，后续写压力可能快速放大

- **问题描述**：当前 SQLite 同时承载 collector、workspace、draft、assets、review、publish、job 等多个子系统。
- **影响范围**：随着 source 数量和 detail fetch 量上升，写放大和锁竞争会显著增加，尤其是 attempts 与 detail fetch 部分。
- **证据路径**：
  - `ArticleWashing-Go/infra/sqlite/provider.go`
  - `ArticleWashing-Go/service/runtime_repos.go`
- **根因分析**：全部状态聚合在单一 provider 上，缺少负载分层策略。
- **建议**：
  - 短期：WAL、批量写入、attempt 限流/归档
  - 中期：collector 与 content runtime 做逻辑分区
  - 长期：为 PostgreSQL 或独立 collector store 预留实现位

### P2：中风险可维护性问题

#### P2-1：collector runtime 存在“内部服务已实现，但非正式入口”的多层语义

- **问题描述**：当前 README 已主动区分“内部服务”“当前运维接口”“cutover 待完成事项”，这是诚实的，但也暴露出能力分层不够统一。
- **影响范围**：团队成员容易误判边界，进而高估当前版本的可运维程度。
- **证据路径**：
  - `ArticleWashing-Go/README.md:84`
- **建议**：
  - 引入清晰 capability matrix
  - 每项能力标记：
    - `implemented`
    - `operator_exposed`
    - `production_ready`

#### P2-2：HTTP/CLI surface 与 service capability 边界尚不稳定

- **问题描述**：当前 source health、runs、scheduler 已对外暴露，但 detail/bridge 仍未形成标准控制面。
- **影响范围**：后续新增接口时容易绕过统一 contract，演变为 ad hoc handler。
- **建议**：
  - 先定义统一 collector API 分层：
    - registry API
    - run API
    - fetch API
    - bridge API
    - diagnostics API

#### P2-3：health diagnostics 已起步，但系统级观测仍偏初级

- **问题描述**：当前已能区分 `auth_missing`、`auth_expired`，但 health 仍以 source-level 检查为主。
- **影响范围**：无法很好回答“为什么这一轮 run 失败率变高”“detail fetch 为什么堆积”等系统级问题。
- **建议**：
  - 增加：
    - per-source failure rate
    - queue depth
    - last successful detail fetch time
    - bridge lag
    - auth expiry suspicion counters

#### P2-4：测试覆盖虽广，但仍偏功能通过，缺少生产边界验证

- **问题描述**：当前已有大量 service/handler/integration tests，这是优势；但对并发、恢复、积压、reconciliation 的验证仍不足。
- **影响范围**：随着 source 数量增长，问题更可能出现在并发与恢复层，而不是 happy path。
- **建议**：
  - 增加：
    - scheduler restart recovery tests
    - worker pool backpressure tests
    - retry exhaustion tests
    - duplicate entry flood tests
    - bridge reconciliation tests

## 四、第二部分：重构与演进路线图

### 阶段 A：生产切换前的最小必要整改

目标：让当前 collector 从“能跑”变成“可被运维和可信切换”。

优先项：

- 补齐 detail fetch / bridge 的正式运维入口（HTTP / CLI）
- 建立 collector task model：
  - hotlist
  - detail
  - bridge
- 建立 bridge reconciliation
- 将 migration matrix 与 cutover checklist 绑定
- 明确生产切换门槛：
  - critical sources fully migrated
  - full validation passed
  - DataCollection-only source count = 0

### 阶段 B：collector runtime 重构

目标：降低 source 持续增长时的耦合与风险。

建议项：

- 抽离 plugin config DTO
- 抽离 collector orchestrator
- 将 scheduler 从“loop + runOnce”升级为“planner + queue + worker”
- 统一 source capability schema
- 增加 attempt / queue / bridge lag observability

### 阶段 C：性能与并发优化

目标：提升 source 与 entry 规模增长时的稳定性。

建议项：

- detail fetch worker pool 独立化
- entry queue / detail queue / bridge queue 分离
- backpressure 机制
- attempt 批量写入
- collector writes 与 content writes 做逻辑分区
- 压测至少验证：
  - `20+ sources/run`
  - `500+ entries/run`
  - `50 article fetches/min`

### 阶段 D：配置治理与安全治理

建议项：

- 统一 source config schema version
- secret refs 与 runtime resolved secret 分离存储
- auth error 分类标准化
- source enable/disable 改为 DB + workspace 配置双层治理
- 对 cookie/header auth 增加 expiration suspicion metrics

### 阶段 E：CI/CD 与交付治理

建议项：

- CI 增加 collector-focused job：
  - plugin tests
  - scheduler tests
  - integration tests
- 落地覆盖率门槛：
  - collector core >= 85%
  - source plugins >= 70%
- 增加 fixture drift detection
- 增加 migration consistency check
- 增加 smoke profile：
  - run-once
  - detail fetch
  - bridge

## 五、生产切换前建议验收门槛

以下条件必须全部满足：

- critical source 全迁移完成
- detail fetch 与 bridge 具备正式运维入口
- scheduler 具备恢复与任务重试能力
- health/status 能回答 source、queue、attempt、bridge 层面的真实状态
- collector 核心覆盖率达到目标
- integration + recovery + backpressure tests 达标
- `go test ./...` 稳定通过
- `DataCollection` 不再承担任何生产 source 的唯一实现

## 六、最终审计结论

最终结论分两句：

- **架构判断**：当前 `ArticleWashing-Go` 的 collector 融合方向是正确的，且已经明显优于继续把 `DataCollection` 作为长期主平台。
- **交付判断**：当前版本仍属于“具备生产演进基础、但尚未完成生产切换闭环”的状态，不能把“已完成首批 Go collector 迁移”表述成“已完全完成 DataCollection 替代”。

可以用更简短的话概括：

- 现在已经有一个正确的 Go 主平台方向
- 但当前 collector 版本还需要一轮面向运行闭环、恢复能力和真实 cutover 的整改，才能达到生产级切换标准
