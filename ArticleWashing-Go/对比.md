# ArticleWashing-Go 与 ArticleWashing 现状对比

> 这份文档描述的是当前仓库中的真实状态，不是早期重写设想，也不是性能宣传材料。

---

## 结论先行

当前可以明确下结论：

- `ArticleWashing-Go` 已完成对 `ArticleWashing` 的**主链路功能等价替代**。
- 这个结论基于此前确定的标准：**功能等价替代 + 覆盖当前实际可用主链路**。
- 这不等于 Go 版 100% 复刻 Python 中所有历史兼容层、旧命名、旧接口细节；它表示 Go 版已经能够接手当前真正有业务价值的运行链路。

主链路指的是：

- workspace/config
- bundle ingestion
- article workspace lifecycle
- formatting/render/validate/assets
- review/publish gate
- workflow/jobs/automation
- HTTP API / CLI 入口

---

## 替代判断标准

这次对比不是看“目录像不像”，而是看以下问题是否都成立：

1. Go 是否能独立吃下 `DataCollection` 产物并导入系统
2. Go 是否能独立完成 draft -> render -> validate -> asset 流程
3. Go 是否能独立完成 review -> publish gate -> publish history
4. Go 是否能独立提供 automation / jobs / workflow / status / health / retry 能力
5. Go 是否已经有 HTTP 与 CLI 的正式入口

当前这些条件都已经满足。

## 1. Workspace / Config

- `ArticleWashing/src/content_hub/domain/workspace/models.py`
- `ArticleWashing/src/content_hub/application/services/config_service.py`

- `workspace init`
- `workspace show-config`
- `workspace resolve-config`
- `workspace doctor`
- secret 引用解析

### Go

Go 版对应能力已经实现于：

- `ArticleWashing-Go/service/workspace_config.go`

- Go 已经具备 workspace-first 配置模型

结论：**已替代**。

## 8. 为什么现在可以说“已可替代”

在第一次对比时，我给出的结论是“还不能完全取代”，原因主要有：

- workspace/config 还没完整落地
- ingestion 还没真正接主路径
- formatting / assets / validation 不完整
- review / publish gate 不完整
- automation 与 workflow 还偏骨架

这些缺口现在都已经补上了。

所以当前判断已经变化为：

- `ArticleWashing-Go` **已完成主链路替代**
- 替代结论基于当前代码状态，而不是重写计划
- 该结论已经有 `go test ./...` 全量通过作为当前验证基础

---

## 9. 仍然存在的边界差异

这些差异存在，但不构成“不能替代主链路”的阻塞：

- Go 不保证 100% 复刻 Python 的历史兼容层
- 某些接口语义不是逐字一致，而是“行为等价”
- TUI 不是全部运维能力入口
- daemon 的 transport 语义经过了真实化收敛，而不是机械模仿 Python

这些差异更准确的定义是：

- **实现差异**
- **接口细节差异**
- **历史兼容差异**

而不是主链路能力缺失。

---

## 10. 最终结论

最终结论可以明确写成：

> `ArticleWashing-Go` 已完成对 `ArticleWashing` 的主链路功能等价替代，当前可以作为默认主实现使用。

更完整的边界说明是：

- 替代范围：当前实际可用主链路
- 替代标准：功能等价，而非历史兼容层逐字复刻
- 当前状态：可以切换，不再需要依赖 Python 版承担主业务链路

这也是后续更新 `README.md` 与项目说明文档时应采用的表述口径。
