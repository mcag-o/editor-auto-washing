# ArticleWashing-Go 与 ArticleWashing 现状对比

> 这份文档描述的是当前仓库中的真实状态，不是早期重写设想，也不是性能宣传材料。

---

## 结论先行

当前可以明确下结论：

- `ArticleWashing-Go` 已完成对 `ArticleWashing` 的**主链路功能等价替代**。
- 这个结论基于此前确定的标准：**功能等价替代 + 覆盖当前实际可用主链路**。
- 这不等于 Go 版 100% 复刻 Python 中所有历史兼容层、旧命名、旧接口细节；它表示 Go 版已经能够接手当前真正有业务价值的运行链路。

主链路指的是：

- workspace/config
- collector hotlist mainline + bundle ingestion
- article workspace lifecycle
- formatting/render/validate/assets
- review/publish gate
- workflow/jobs/automation
- HTTP API / CLI 入口

---

## 替代判断标准

这次对比不是看“目录像不像”，而是看以下问题是否都成立：

1. Go 是否能独立执行当前已暴露的 collector 主链路（source registry / hotlist run / scheduler control）
2. Go 是否还能兼容吃下历史 bundle 并导入系统
3. Go 是否能独立完成 draft -> render -> validate -> asset 流程
4. Go 是否能独立完成 review -> publish gate -> publish history
5. Go 是否能独立提供 automation / collector scheduler / jobs / workflow / status / health / retry 能力
6. Go 是否已经有 HTTP 与 CLI 的正式入口

当前这些条件都已经满足。

## 2. Collector Runtime / Ingestion

### 当前生产语义

这里需要先澄清口径：当前仓库状态下，`DataCollection/` 不再应被描述为生产 collector 主路径。

更准确的现状是：

- `ArticleWashing-Go` 已内置 collector runtime
- Go runtime 已对外提供 source registry、hotlist run listing、scheduler HTTP/CLI
- Go runtime 内部已具备 detail fetch、attempt persistence、bridge-to-workspace 服务
- `DataCollection/` 当前保留为历史实现、fixture/对照来源、未迁移 source 的迁移基线

也就是说，对“采集路径是否已切到 Go”这个问题，当前更准确的回答是：已切到 Go runtime 的 source registry / hotlist run / scheduler 控制面，但 detail fetch 与 bridge 还主要停留在内部服务层，而不是完整公开的运维面。

### Go collector 当前真实范围

当前默认注册到 Go runtime 的 source：

- `baidu`
- `bilibili`
- `github`
- `stackoverflow`
- `v2ex`
- `weibo`

当前状态边界：

- `baidu`、`github`、`v2ex`：已具备 hotlist + detail fetch
- `bilibili`、`stackoverflow`、`weibo`：当前仅 hotlist
- 其余 `DataCollection/` source：尚未迁移

这个边界需要再细分成三层：

- 内部服务层：detail fetch 与 bridge 已实现
- 当前对外运维层：source list/health、run list/detail、scheduler control
- cutover 待完成层：detail fetch/bridge 的正式入口、source-by-source 生产验证、未迁移 source 补齐

### Python

Python 历史上主要承担的是 bundle ingestion、workspace article 创建与后续内容链路，不包含当前这轮 Go collector runtime 的内置执行模型。

Python 通过 ingestion service 与 automation CLI 处理：

- bundle import
- incoming / processed / failed
- retry-failed
- workspace article 创建

关键入口：

- `ArticleWashing/src/content_hub/application/services/ingestion_service.py`
- `ArticleWashing/src/content_hub/interfaces/cli.py`

### Go

Go 对应能力现在分成两层，而且都在 `ArticleWashing-Go` 内：

采集层：

- `ArticleWashing-Go/collector/service/registry.go`
- `ArticleWashing-Go/collector/service/run_service.go`
- `ArticleWashing-Go/collector/service/article_fetch_service.go`
- `ArticleWashing-Go/collector/service/bridge_service.go`
- `ArticleWashing-Go/collector/scheduler/service.go`
- `ArticleWashing-Go/service/collector_runtime.go`

导入/工作区层：

- `ArticleWashing-Go/service/ingestion_pipeline.go`
- `ArticleWashing-Go/infra/filesystem/bundle_router.go`
- `ArticleWashing-Go/infra/sqlite/ingestion_repo.go`
- `ArticleWashing-Go/infra/sqlite/article_workspace_repo.go`
- `ArticleWashing-Go/transport/http/handlers/ingestion.go`
- `ArticleWashing-Go/cmd/cli/main.go`

判断：

- Go 已能独立完成 collector hotlist 主链路并对外暴露运行入口
- Go 已内置已迁移 source 的 detail fetch 与 bridge 服务实现
- Go 仍兼容历史 bundle import，用于过渡和回灌
- 已能做 routing / retry-failed / ingestion record / workspace record

结论：**已替代**。

## 8. 为什么现在可以说“已可替代”

在第一次对比时，我给出的结论是“还不能完全取代”，原因主要有：

- workspace/config 还没完整落地
- ingestion 还没真正接主路径
- formatting / assets / validation 不完整
- review / publish gate 不完整
- automation 与 workflow 还偏骨架

这些缺口现在都已经补上了。

所以当前判断已经变化为：

- `ArticleWashing-Go` **已完成主链路替代**
- 替代结论基于当前代码状态，而不是重写计划
- collector 当前已暴露的运维主链路已经在 Go runtime 内闭环，不再以 `DataCollection/` 作为默认执行路径
- 该结论已经有 `go test ./...` 全量通过作为当前验证基础

---

## 9. 仍然存在的边界差异

这些差异存在，但不构成“不能替代主链路”的阻塞：

- Go 不保证 100% 复刻 Python 的历史兼容层
- Go collector 只覆盖当前已迁移 source，不代表 `DataCollection/` 全部 source 已经完成切换
- Go collector 的 detail fetch / bridge 当前还不是正式的一线运维接口
- 某些接口语义不是逐字一致，而是“行为等价”
- TUI 不是全部运维能力入口
- daemon 的 transport 语义经过了真实化收敛，而不是机械模仿 Python

这些差异更准确的定义是：

- **实现差异**
- **接口细节差异**
- **历史兼容差异**

而不是主链路能力缺失。

---

## 10. 最终结论

最终结论可以明确写成：

> `ArticleWashing-Go` 已完成对 `ArticleWashing` 的主链路功能等价替代，当前可以作为默认主实现使用。

更完整的边界说明是：

- 替代范围：当前实际可用主链路
- 替代标准：功能等价，而非历史兼容层逐字复刻
- 当前状态：可以切换到 Go 的当前运维主入口，但真实生产 cutover 仍需要补足 detail fetch / bridge 操作面和 source-by-source 验证

这也是后续更新 `README.md` 与项目说明文档时应采用的表述口径。
