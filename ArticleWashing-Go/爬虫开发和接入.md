# 爬虫开发和接入

本文档面向后续在 `ArticleWashing-Go` 中继续迁移 `DataCollection` 平台能力的开发人员。

目标不是单独写出一个“能跑一下”的抓取脚本，而是把每个站点实现为可维护、可测试、可配置、可接入统一运行时的 Go 插件，最终逐步替代 `DataCollection`。

---

## 1. 文档目标

本文档回答四件事：

1. 单个站点爬虫应该做到什么程度才算合格
2. 新站点应放到哪里、按什么接口实现
3. 如何接入当前 `ArticleWashing-Go` 的配置、认证、重试、运行时链路
4. 如何验收“该站点已不再依赖 `DataCollection` 旧实现”

---

## 2. 基本原则

### 2.1 不是独立脚本，而是统一运行时插件

后续开发的站点爬虫，不应停留在：

- 一个独立 Go 文件
- 一个可手工运行的实验程序
- 一个只会打印 JSON 的临时脚本

必须最终融入当前 Go 侧统一 collector runtime：

- 统一 source id
- 统一插件接口
- 统一配置入口
- 统一重试/超时/认证策略
- 统一 source sync 元数据持久化
- 统一 run / health / scheduler 路径

### 2.2 优先复用现有运行时能力

已经存在的能力，不要在站点内部重复实现：

- HTTP 客户端构建：`collector/runtime/http_factory.go`
- auth 注入：`collector/runtime/auth_factory.go`
- source 策略解析：`collector/runtime/policy_resolver.go`
- 重试分类与退避：`collector/httpclient/retry.go`
- runtime 适配：`collector/service/runtime_plugin_adapter.go`

站点代码应优先只关心：

- 请求路径
- 响应结构
- HTML 选择器或 JSON 字段映射
- 标准化逻辑
- 站点特有的业务规则

### 2.3 先进入体系，再补能力

对于一个尚未迁完的平台，合理顺序是：

1. 在配置中定义 source
2. 明确占位目标、TODO、迁移参考
3. 提供 placeholder 或最小 plugin 骨架
4. 补 hotlist
5. 补 detail fetch
6. 补 normalize / bridge 需要的字段
7. 补 fixture / test / health / auth / 诊断

不要反过来先做很多零散实现，再回头接入体系。

## 3. 当前统一接入点

后续开发最常用的目录如下：

- 平台配置：`ArticleWashing-Go/infra/config/collector_config.go`
- 运行时配置文件：`ArticleWashing-Go/config/config.json`
- 插件接口：`ArticleWashing-Go/collector/plugin/interface.go`
- 真实站点插件：`ArticleWashing-Go/collector/plugin/sources/`
- 运行时策略解析：`ArticleWashing-Go/collector/runtime/policy_resolver.go`
- 认证工厂：`ArticleWashing-Go/collector/runtime/auth_factory.go`
- HTTP 工厂：`ArticleWashing-Go/collector/runtime/http_factory.go`
- runtime 适配层：`ArticleWashing-Go/collector/service/runtime_plugin_adapter.go`
- registry 构建：`ArticleWashing-Go/collector/service/registry.go`
- run service：`ArticleWashing-Go/collector/service/run_service.go`
- source health / sync：`ArticleWashing-Go/collector/service/source_registry_service.go`
- runtime 装配：`ArticleWashing-Go/service/collector_runtime.go`

## 4. 单站点爬虫的完成标准

一个站点若要被视为“已迁入 Go 主系统”，建议至少满足以下标准。

### 4.1 最低可接入标准

- 在 `collector_config.go` 中存在 source 定义
- 在 `config/config.json` 中有对应 source 配置
- 在 `collector/plugin/sources/` 中存在真实插件，不再是 placeholder
- 能进入 registry / source sync / run / health 主流程
- 有最基本测试

### 4.2 实用标准

- 支持 hotlist/list 抓取
- 输出标准化 `HotEntry`
- 支持 runtime config 注入后的运行
- 使用统一 HTTP/auth/runtime 路径
- 对常见失败有清晰错误信息

### 4.3 等价替代标准

- 已覆盖 `DataCollection` 原平台的主要抓取能力
- 若原平台支持 detail，则 Go 版也支持 detail
- 若原平台依赖 cookie/header/token，则 Go 版也支持通过配置接入
- 有 fixture 驱动回归测试
- 健康检查与失败分类能满足运维定位

---

## 5. 新站点开发的标准流程

推荐严格按下面顺序执行。

### 第一步：确认平台定位

先回答这几个问题：

- 这是 JSON API 平台，还是 HTML 平台？
- 只需要 hotlist，还是还需要 detail fetch？
- 是否需要 cookie / header / token / 代理？
- 是否有 `DataCollection` 旧实现可参考？
- 是否有稳定 fixture 可以沉淀？

如果这些问题都没回答清楚，不要急着写正式插件。

### 第二步：补齐配置占位

先在 `ArticleWashing-Go/infra/config/collector_config.go` 中完善该站点定义。

要求至少写清：

- `display_name`
- `aliases`
- `source_type`
- `source_url`
- `status`
- `goal`
- `todo`
- `notes`
- `migration_reference`
- `supports_article`
- `auth_mode`

这里的中文说明不是装饰，而是后续开发导航层。

### 第三步：在配置文件中暴露运行参数

在 `ArticleWashing-Go/config/config.json` 中为该站点写明：

- 使用哪个 `http_client`
- 使用哪个 `retry_policy`
- 使用哪个 `auth_profile`
- `timeout_ms`
- `hotlist_limit`
- `interval_minutes`
- 必要的 source 级 `headers`

后续如果某站点需要特殊策略，应优先在配置中扩展，而不是在插件里硬编码。

### 第四步：实现真实插件

在 `ArticleWashing-Go/collector/plugin/sources/` 下新增或替换该站点插件。

通常应实现：

- `SourceID()`
- `DisplayName()`
- `Aliases()`
- `FetchHotlist()`
- `FetchArticle()`（如果支持 detail）
- `NormalizeHotEntry()`
- `NormalizeArticle()`（如果支持 detail）
- `HealthCheck()`
- `Capabilities()`
- `Descriptor()`

如需进入统一 runtime 注入路径，还应支持：

- `WithSourceConfig(...)`
- `WithHTTPClient(...)`
- `HTTPClient()`

参考：

- API 型：`ArticleWashing-Go/collector/plugin/sources/api_plugin.go`
- Cookie 型：`ArticleWashing-Go/collector/plugin/sources/weibo.go`

### 第五步：接入运行时路径

一个插件即使本身实现完成，也必须能走当前 runtime 路径：

- `PolicyResolver` 解析 source config
- `AuthFactory` 解析 secret ref -> auth injector
- `HTTPFactory` 构造 source-scoped client
- `runtime_plugin_adapter` 将 client 注入 plugin
- `RunService` / `SourceRegistryService` 使用 runtime-aware path 执行

如果你的插件仍必须依赖内部硬编码 client 才能工作，说明接入还没完成。

### 第六步：补测试与 fixture

每个新站点至少补：

- 站点插件测试
- 运行时接入测试
- source sync / run / health 至少一条主流程测试

优先使用 fixture：

- JSON fixture
- HTML fixture
- auth 失败 fixture
- detail/article fixture

目标是后续上游改结构时，能快速定位是哪个 source 坏了。

## 6. 插件实现要求

### 6.1 `FetchHotlist()`

要求：

- 只负责抓取该 source 的热榜/列表
- 不要在这里偷偷做跨站点逻辑
- 不要在这里硬编码全局策略
- 尽量把请求路径、query、headers 以最小必要形式表达

必须输出：

- source id
- external id
- canonical URL
- title
- summary（如可得）
- rank（如可得）
- raw JSON / raw metadata

### 6.2 `FetchArticle()`

若站点支持 detail/article：

- 必须明确 detail 来源是 API、HTML 还是其他接口
- 必须返回 `RawArticle`
- 必须给出 `ContentType`
- 尽量补齐与后续 normalize 相关的 metadata

如果不支持：

- 明确返回 `plugin.ErrArticleFetchNotSupported(...)`

### 6.3 `NormalizeHotEntry()` / `NormalizeArticle()`

要求：

- 做字段标准化，不做多余 I/O
- 错误信息要能说明是哪个字段、哪个 source 出错
- 保留必要 raw 内容方便回溯

### 6.4 `HealthCheck()`

要求：

- 尽量走真实最小请求路径
- 返回 `healthy` / `unavailable` / `auth_missing` / `auth_expired` 等语义
- 不要把所有错误都模糊成同一种状态

但也不要在插件内重复实现一整套 auth framework；优先复用 runtime 注入结果。

### 6.5 `Descriptor()`

这是 source sync 持久化的关键描述面。

要求尽量提供：

- `Enabled`
- `ScheduleEnabled`
- `IntervalMinutes`
- `TimeoutMS`
- `HotlistLimit`
- `DetailFetchEnabled`
- `Concurrency`
- `AuthMode`
- `Headers`
- `RetryPolicy`
- `Options`
- `Metadata`

说明：

- 这些字段不一定全都最终由插件自己决定
- 当前系统会把 resolved runtime metadata 和 descriptor 结合起来持久化
- 因此 descriptor 应尽量表达“插件能力”和“最小默认描述”，不要重复硬编码最终策略

## 7. 配置接入要求

### 7.1 source 定义必须完整

每个 source 在 `CollectorSourceDef` 中至少需要：

- `DisplayName`
- `SourceType`
- `SourceURL`
- `HTTPClient`
- `RetryPolicy`
- `AuthProfile`
- `TimeoutMS`
- `Headers`
- `Status`
- `Goal`
- `Todo`

### 7.2 优先使用 profile，而不是 source 内硬编码

优先顺序应是：

1. 在 `defaults` 中定义默认策略
2. 在 `http_clients` / `retry_policies` / `auth_profiles` 中定义命名策略
3. source 只引用 profile 并做少量 override

不要优先选择：

- 在插件构造函数里写死 timeout
- 在插件里写死认证头拼接规则
- 在插件里写死重试策略

### 7.3 secret 统一通过 ref

敏感信息不能写死在插件里。

应该使用：

- `env.WEIBO_COOKIE`
- `env.XUEQIU_COOKIE`
- `env.GITHUB_TOKEN`
- 其他 `env.*` 风格 ref

当前 collector runtime 已有真实 secret resolver 路径，至少覆盖 `env.*`。

---

## 8. 认证接入要求

### 8.1 不要在插件内部解析 secret

禁止再新增这类做法：

- `os.Getenv(...)` 直接写在插件里
- 插件内部自己找 cookie/token
- 插件内部 fallback 默认 secret ref

这些行为现在应该通过：

- `ResolvedAuthConfig`
- `AuthFactory`
- `runtime_plugin_adapter`

完成。

### 8.2 Cookie / Header / Token 的处理方式

站点如果需要认证：

- source config 指向 `auth_profile`
- source config 写 `CookieSecretRef` / `HeaderSecretRef`
- runtime resolver 解析 auth profile
- auth factory 构造 injector
- HTTP factory 构造 client
- runtime adapter 将 client 注入插件

站点插件只消费注入后的 client，不负责 secret 解析。

---

## 9. HTTP 与重试接入要求

### 9.1 不要自行 new 一套临时 client 逃逸运行时

如果插件在真实运行路径里还是绕开 `HTTPFactory`，那这个插件就不算完成接入。

### 9.2 使用统一退避与分类能力

当前可复用能力包括：

- `RetryClassifier`
- `ExponentialBackoff`
- `MaxWait`
- `Jitter`

原则：

- source-specific retry policy 应优先来自配置
- 站点内部不要重新写一套 sleep/retry loop

### 9.3 Header 合并规则

一般规则：

- profile headers 提供默认值
- source headers 做局部覆盖
- runtime 注入 auth header
- 插件不应在真实路径中覆盖掉 runtime 已决定的 header 组合

---

## 10. 测试要求

### 10.1 单站点至少要有这些测试

- `FetchHotlist` 成功
- `FetchHotlist` 失败
- `HealthCheck` 成功
- `HealthCheck` 失败
- 如有 detail：`FetchArticle` / `NormalizeArticle`

### 10.2 接入测试

除了插件测试，还应有接入层测试：

- source sync 后 metadata 是否正确
- runtime resolver 是否正确解析 profile/defaults/source override
- auth factory 是否正确处理 secret ref
- HTTP factory 是否把 timeout/retry/baseURL 落到 client
- service path 是否真正使用 runtime-aware client

### 10.3 fixture 要求

建议至少沉淀：

- 正常响应 fixture
- 空响应 / 结构变更 fixture
- auth 失败 fixture
- detail 页面 fixture

fixture 应尽量放在现有测试数据结构附近，避免散落。

---

## 11. 占位骨架替换要求

当前很多平台还是 placeholder。替换时建议按以下步骤做：

1. 保留原 source id，不要改名
2. 保留原 `goal` / `todo` / `migration_reference`，直到真实实现稳定
3. 新增真实插件实现
4. 在 registry 中让真实插件替代 placeholder
5. 确认 sync / run / health / scheduler 路径都正常
6. 补测试
7. 再视情况把占位说明简化为“已实现 + 后续维护事项”

不要直接删掉占位信息后再慢慢补，因为这样会丢掉迁移上下文。

---

## 12. 参考 `DataCollection` 的正确方式

`DataCollection` 现在更适合作为：

- 迁移参考
- 平台行为样本
- fixture 来源
- 旧平台实现知识库

不建议把 `DataCollection` 当成必须逐行翻译的目标。

迁移时应提取的是：

- endpoint
- query/header/cookie 需求
- 字段映射逻辑
- 认证要求
- 页面结构与失败模式

而不是强行复刻旧工程结构。

---

## 13. 一个站点何时可以宣布“已迁入 Go”

建议至少满足：

- placeholder 已被真实插件替代
- 运行路径走统一 runtime
- 配置、认证、HTTP、重试可由统一体系控制
- `go test` 覆盖该站点核心行为
- 不再依赖 `DataCollection` 旧脚本运行

如果只实现了热榜但没有 detail，应明确标为：

- `partial`

如果仍只是说明和骨架，应标为：

- `placeholder`

不要把“能抓到一点数据”误标为“已完成替代”。

## 14. 推荐的开发验收清单

每做完一个站点，建议按下面清单自查：

- [ ] source 配置已补齐
- [ ] `config/config.json` 已暴露必要参数
- [ ] 已实现真实插件，不再是 placeholder
- [ ] 已支持 `FetchHotlist`
- [ ] 如需 detail，已支持 `FetchArticle`
- [ ] 已实现标准化输出
- [ ] 已接入 runtime policy resolver
- [ ] 已接入 auth factory
- [ ] 已接入 HTTP factory
- [ ] 已接入 run / health 主路径
- [ ] 已有 fixture
- [ ] 已有回归测试
- [ ] 已标明当前状态：`implemented-equivalent` / `implemented-partial`

---

## 15. 当前最重要的纪律

后续所有新站点开发，请尽量遵守这三条：

1. 先接入统一体系，再补站点细节
2. 先写清配置与工作目标，再写代码
3. 不要把 secret、retry、timeout、auth 重新硬编码回插件内部

只要持续按这个文档推进，后续逐站点替换完成后，`ArticleWashing-Go` 就可以真正完成对 `DataCollection` 的最终替代。
